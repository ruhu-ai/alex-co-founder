Co-Founder Enterprise Architecture

The authoritative architecture description of Co-Founder — an AI co-founder for solo founders, built as a general workflow engine and shipped with its first workflow: the end-to-end funding & program application pipeline. This document covers system context, runtime and logical structure, the application state machine, data authority, the governance gates, integration seams, security, deployment, reliability, operations, and evaluation — written to the standard an enterprise architecture review board expects, and checkable against the repository it describes. Co-Founder was built for the All Things Agentic hackathon (Collaborative Partner) and engineered to outlive it as Ruhu Inc.'s operations engine.

System Context And Scope

What Co-Founder is: a persistent business partner with durable memory of the company that runs an end-to-end application pipeline — discover programs from messy sources, score them against a Founder Profile, interview to fill gaps, draft in the founder's voice, learn from feedback, pre-fill the real portal form behind a human approval gate, submit, and track follow-up. Architecture Principles And Invariants

These are not aspirations: each is enforced by code, a Firestore transaction, a before_tool_callback, or a golden eval, and changing one requires changing the governing specification. They bind every section that follows (docs/README.md, AGENTS.md).

P1 · The state machine grounds everything

The agent reads workflow position from session state ({current_step} and siblings injected into the instruction), never from chat history. State is seeded in a before_agent_callback and mirrored durably in Firestore. No replayed conversation, no hallucinated intermediate step.

P2 · Two planes, one authority

Gemini agents investigate, score, interview, draft, and distil. Typed application services own state transitions, approval validity, idempotency, and every mutation. Model output can become a proposal — never authority.

P3 · Tools return errors as data

A tool never raises to the model. _common.run() converts any exception into {status:"error", error:True, message:…} so the model explains and recovers. failed() is the guarded truthiness check at that boundary.

P4 · Dormancy by default

No polling loops, no resident processes. The container scales to zero; Cloud Scheduler → Pub/Sub, portal webhooks, and mailbox pushes wake it. On wake the resume handler applies a state_delta atomically before the next inference.

P5 · No agent invokes another agent

The five sub-agents are an ADK transfer graph; the LLM swaps instruction+tools per agent. There is no AgentTool anywhere. The distiller is a separate standalone App, driven synchronously from the feedback path. Isolation is structural.

P6 · Human approval precedes every irreversible action

Submit, send email, book a meeting, and create a portal account each require a server-resolved, single-use approval the model never sees. Autonomous by default; the agent escalates only when blocked. This is a feature, not a limitation.

P7 · Guards live in code, not prompts

Anything that must happen every time — the G3 portal gate, the staleness fence, document grounding, idempotency — is a before_tool_callback or a transaction, never an instruction. "Ask in the prompt and it complies most of the time; ask in code and it complies every time."

P8 · Every external action is idempotent and audited

Form fills, submissions, sends, and bookings carry a derived idempotency key and write an append-only audit row (actor / action / target / result / key). Histories are never rewritten.

P9 · Everything external is untrusted data

Web pages, PDFs, emails, and portal DOM are data, never instructions. Browsing is SSRF-guarded; ingested content is injection-scanned (reads allowed, actions suspended on a hit); a grounding guard blocks fabricated figures from reaching a produced document.

P10 · One engine, many workflows

The core is domain-agnostic (Opportunity, PipelineStore, ApprovalGate); the Scout does not know what a "grant" is — it extracts whatever schema the active workflow defines. Adding a workflow is a declarative definition plus a small adapter, not a rewrite.

Enforcement, not prose. Where this document states a rule, the repository prefers a deterministic check: the transition table (state_schema.can_transition), the two form-filler gates (verify_before_action), the drafter's grounding guard (enforce_document_grounding), the transactional approval claim (firestore.claim_approval), and the six golden eval sets that assert the agent refuses to skip a gate.

Dependency rules

  1. Tools depend on services, never the reverse; a tool is a thin adapter that converts a service result into model-facing data.
  2. The orchestrator and sub-agents never import each other; control moves only by ADK transfer, and the distiller only through its own App.
  3. Only the form-filler holds portal-touching, submitting tools. The drafter has no submit tool at all; the vision-recon loop has no submit action by construction.
  4. Every service function that mutates workflow state routes through pipeline_service.advance_application / the Firestore transaction helpers — never an ad-hoc write.
  5. The model never receives an approval token, a secret, or a credential as a tool argument; credentials are looked up by host at execution time.
  6. Core modules use generic names (Opportunity, PipelineStore, ApprovalGate); domain specifics live in workflows/ config, not core code.

Adoption profile

The active workflow (grant_applications.yaml) supplies sources, the entity schema the Scout extracts, drafting templates, and the approval policy. Future workflows (investor outreach, customer discovery, hiring, compliance) load as new definitions against the same sub-agents, Founder Profile, and pipeline store — target, by design.

The workflow is an explicit state machine, not a conversation. current_step is injected into the instruction so the model always sees exact position; every transition is re-checked server-side by can_transition against the table below, and mirrored to the Firestore application record. A step not in a source set's value is illegal — no skipping.

Amber chevrons are human-gated states. Gate G3 (staleness fence + step gate) governs every portal-touching tool; Gate G2 requires a server-resolved approval before a submit. The reject/edit edge is the adaptation loop — feedback returns the section to DRAFTING and the next draft cites the distilled rule.

Data Architecture And Authority Model

Firestore · 17 collections

  • The workflow authority: opportunities, applications, profiles, feedback, approvals, audit, browser_runs (+ actions ledger), ingestions, evidence_checks, oauth_states, integrations, gmail_state, alex_mail_state, portal_registrations, source_state, documents, document_versions.
  • Deterministic doc ids (sha256 of a dedup key) and transactions prevent duplicates; transitions use compare-and-set on expected_state.

Founder Profile · long-term memory

  • One document per founder: version, facts, voice_rules, canonical_answers, rejection_history, decision_patterns.
  • The "constantly adapts" evidence. Every write is versioned in a transaction and audited as agent:distiller / profile_update; apply_profile_update is the only write path.

Idempotency & audit

  • Submit derives its key deterministically (sha256(founder:app:submit)[:24]); find_successful_action short-circuits a repeat.
  • The append-only audit collection is never updated — actor / action / target / result / idempotency_key / detail (≤500 chars); no secrets, no PII beyond refs.

The Governance Gates: One Action, Four Independent Checks

Every consequential path is a chain of independent gates enforced in code, not prompts. The read/browse path suspends on danger; the write/submit path releases without mutating. No gate shares discretion with the one before it.

Both paths are chains of code-enforced gates. The submit approval is content-bound and single-use: submit_form takes no token argument — resolving the approval server-side keeps the secret out of the model's tool call — and the approval is consumed only after a confirmed receipt, so a transient portal failure preserves the grant.

The approval gate, precisely

request_approval creates a PENDING, session- and founder-bound approval with token=None and returns only an id. The founder grants it in the UI; only then is a token minted, living solely in the Firestore doc. To act, the tool resolves a GRANTED, unexpired, unconsumed approval server-side (no token passes through the model), and claim_approval flips GRANTED→CONSUMED in one transaction. Email and calendar sends are content-bound: a prompt-injected re-invocation with swapped arguments still sends the approved payload (audited drift_ignored).

The two form-filler guards

verify_before_action runs before every form-filler tool. G3: sign_in, open_portal, fill_fields, submit_form may run only in APPROVED / FORM_FILLING / AWAITING_SUBMIT_APPROVAL. Staleness fence: before a fill or submit, the live form's field-name signature must match the one captured at inspection (a persisted, not temp:, key so it survives the cross-turn fill→approve→submit flow); a mismatch — e.g. the portal's ?v=2 field rename — returns an error telling the model to re-inspect, never to guess.

Security Architecture

Identity and access

  • Cloud Run stays --allow-unauthenticated at the platform layer (portal webhooks and Pub/Sub push carry no IAM identity); the app enforces its own gate.
  • A founder-token middleware gates everything except /health, /webhooks/, /tasks/. Token via Bearer / X-App-Key / cookie / ?key=, compared with hmac.compare_digest. Missing token in production (K_SERVICE) → 503; non-founder → 401.
  • Task and deadline routes verify a Google-signed OIDC token minted for this service by the scheduler-invoker service account — signature, audience, and caller email all checked; the portal webhook verifies X-Portal-Token.
  • The ?key= bootstrap sets an HttpOnly cookie then 303-redirects to strip the token from the URL (history/referer hygiene).

Model and content safety

  • Everything the agent ingests from the open web, PDFs, or email is untrusted data. Instruction-shaped inbound mail is withheld from the prompt entirely; the remainder is wrapped in explicit untrusted-content delimiters.
  • Browsing is SSRF-guarded (DNS-pinning validating proxy, GET/HEAD only, private/reserved/ metadata IPs blocked including legacy IPv4 spellings, credential URLs rejected).
  • An injection scan suspends actions (not reads) on a hit; a bot-challenge detector freezes the run and returns needs-human — Alex never solves CAPTCHAs.
  • A drafter grounding guard blocks a produced document that cites a figure not present in approved sections, profile facts, or quotable programme fields, and catches the wrong applicant name.

Secrets and credentials

  • Portal credentials, OAuth refresh tokens, and webhook/app tokens live only in Secret Manager, fetched by name at execution time; the deploy binds sensitive env via --set-secrets, and refresh tokens are created only by the in-app Connect flow.
  • A logging.Filter redacts any registered secret from the log message, traceback, and stack. Structured logs carry metadata only (notice_len, session_id, author) — never prompt/tool content, email excerpts, or PII.
  • The model never receives a token, password, or credential as a tool argument.

Tool scoping & fail-closed

  • Tools are scoped per capability: the drafter has no portal or submit tool; the vision recon loop's action set excludes submit by construction; only the form-filler can submit, and only through the gate chain.
  • Every verifier keys its dev-open behavior on the absence of K_SERVICE, so production fails closed: no app token → 503, no portal/OIDC token → 401, BROWSE_OPEN_WEB asserted false at deploy.
  • The ADK admin API (/apps, /run*, docs) is stripped from the app before any request is served.
Safety headline — zero unauthorized submissions. The gate is enforced in code, not prompts: the drafter physically cannot submit; a submission requires a server-resolved, single-use approval token the model never sees; guards live in before_tool_callbacks; and three golden eval sets prove the agent refuses to submit before approval — under "I trust you," under deadline pressure, and idempotently.

Reliability And Continuity

Continuity is structural: there is no long-lived process whose loss can lose work. The agent sleeps between events; recovery is a fresh turn rebuilt from durable rows; repeated effects are impossible by key rather than unlikely by care.

Continuity of multi-week work

  • Dormancy + resume. The container may scale to zero for days while an application waits on the founder or a deadline. A Pub/Sub tick, portal webhook, or mailbox push wakes it; the resume handler applies the state_delta atomically before the next inference — no replayed chat history, no hallucinated intermediate step.
  • Durable re-drive. Portal confirmations enqueue the multi-minute wake on the co-founder-events Cloud Tasks queue (concurrency 1, up to 8 attempts) rather than blocking the webhook; the ack is fast, the work is guaranteed.
  • Crash-safe browser actions. Each browse action is reserved and PREPARED before execution; a restart mid-action leaves it UNCERTAIN and it is never replayed.
  • Transactional transitions. Application state moves by compare-and-set on the expected state; two concurrent writers cannot both advance.

What is deliberately not promised

  • Not an autonomous submitter — a human approval gate always precedes a submission; the agent escalates when blocked rather than guessing.
  • Not a general-purpose "works on any website" browser — the target is a small set of real portals plus the self-hosted mock portal as a reliable demo fallback.
  • Not cross-instance browser sharing — the co-founder service runs a single browser-owning instance (max-instances 1) by design.
  • The StaleSessionError retry is bounded to one attempt with a double-append guard, then re-raises; the wake notice is never applied twice.
Idempotency, layered. Opportunities dedupe on a deterministic doc id; the submit derives its key from founder:application:submit so a retry recomputes the same key and find_successful_action short-circuits; email/calendar approvals are single-use and content-bound; discovery skips unchanged sources by content hash. Repeated effects are prevented by constraint, then confirmed by an append-only audit row.

Observability And Operations

Telemetry model

  • OpenTelemetry GenAI instrumentation → Cloud Trace; completions uploaded to GCS as JSONL. The on-switch is LOGS_BUCKET_NAME; capture runs in NO_CONTENT (metadata-only) mode by default, so prompt/response bodies are not logged.
  • Structured logs are JSON with metadata only — author, invocation id, notice length, session id — never prompt or tool content, email excerpts, or PII.
  • Cloud Trace joins spans to the reasoning chain end-to-end for production-readiness proof.

Operator surfaces

  • Pipeline board (/api/pipeline): opportunities by state, in-flight applications, urgency.
  • Browser panel (/api/browser/state): the live browse/fill run rendered from streamed screenshots — the founder watches the agent work without an OS window.
  • Audit trail (/api/audit): the append-only action log, newest first, for who/what/when/result of every consequential step.
  • Approvals inbox and per-application detail (drafts, fill report, evidence check, pending approval).
The audit log is the operational spine. Every side-effectful path writes one append-only audit row with a namespaced actor (founder:{id}, agent:form_filler, agent:distiller, system:portal, system:discovery). Refused actions are audited too — a bot challenge, a G3 violation, an SSRF block — so a reviewer can see not just what happened but what the agent declined to do.

  • A stateful in-memory Firestore fake at the module boundary; injectable model/HTTP seams so no test touches a live model, network, or GCP.
  • Real Playwright Chromium against a local fixture site through an injected validating proxy — SSRF encodings, injection suspension, bot-challenge fail-closed, action budgets, idempotent replay.
  • Assertions are behavioral (state mutations, audit rows, decoded RFC822 bytes, idempotency-key replays), not smoke.
Independent draft verification — a Gemma second opinion (docs/20). When enabled (GEMMA_EVIDENCE_CHECK_ENABLED), a separate model — Gemma (gemma-4-26b-a4b-it-maas via Vertex MaaS), a different family from the Gemini producer — runs a semantic check on a completed draft. The input is a deterministic, allowlisted, PII-stripped evidence pack (≤60k chars); the run is leased and idempotent on an input hash via the evidence_checks collection, with a 25 s wall-clock cap. It flags only CONTRADICTION, OVERSTATED_EVIDENCE, and CROSS_SECTION_CONFLICT; every finding must be an exact draft substring citing a supplied evidence ref, and the suggested next step is code-authored, never model-written. It is advisory by construction — a dead or slow model must never hold a finished draft in DRAFTING (proven by test_model_failure_still_reaches_awaiting_review) — so it is a second safeguard behind the drafter's grounding guard, never the only one.

The Gemini tiers publish on the Vertex global endpoint; both text models wrap HttpRetryOptions(attempts=3). Each assignment is one variable (ADK_MODEL, REASONING_MODEL, LITE_MODEL, LIVE_MODEL). The evidence checker adds a distinct Gemma family (Model-as-a-Service; the Gemini-API name gemma-4-26b-a4b-it would 404 against Vertex) behind its own GEMMA_EVIDENCE_CHECK_ENABLED switch — model breadth and an independent verifier in one component.

Decision records

  • Reasoning on Flash, not Pro-preview. The reasoning tier ran on gemini-3.1-pro-preview until it fabricated a company on the drafting task (now caught model-independently by the grounding guard) and a Pro→Pro chain blew a 600 s redraft budget; a preview endpoint is also a poor bet for a submission that must stay live for judging. Reverted to gemini-3.6-flash; the seam remains one variable to change.
  • adr/001 — agent identity. A named persona (Alex) with a role mailbox (alex@ruhu.ai) and no human-body claims; pinned by the persona_identity eval.
  • adr/002 — meeting presence. Calendar scheduling with a notes ladder; the create-event write is approval-gated and content-bound.
  • docs/19 §P1.5–1.6 — real A2A + embeddings. The portal is a genuine A2A agent; semantic retrieval has a deterministic fallback so it never becomes an outage.
  • docs/20 — Gemma evidence checker, advisory not gating. A second model family verifies the draft, but never blocks it: a dead or slow model must still let a finished draft reach review. Independent verification without a new failure mode.
The engine, stated once more. Co-Founder is architected as a general workflow engine: shared sub-agents that do not know the domain, a persistent Founder Profile, a generic pipeline store, and a declarative workflow definition. The funding-application pipeline is the one instance built and proven end-to-end; investor outreach, customer discovery, hiring, and compliance are new definitions on the same engine. The boundary is deliberate — the agent does the work; the founder keeps the judgment.
